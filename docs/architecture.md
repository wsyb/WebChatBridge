# 工作原理

## 四个角色

这个项目的核心是让网页版 AI 能够操作用户的本地电脑。但浏览器有安全沙盒，网页无法直接访问文件系统。所以我们需要四个角色协作：

### AI（语言模型）

- **能做**：生成文字、推理、规划
- **不能做**：访问文件系统、执行命令
- **原因**：运行在远程服务器，和用户电脑物理隔离

AI 通过输出特定格式的 tool_call 代码块来下达指令。

### Chrome 扩展

- **能做**：读网页 DOM、检测 AI 输出的文字、和 Native Host 通信、把文字写入输入框
- **不能做**：执行命令、读写文件
- **原因**：运行在浏览器沙箱里，没有操作系统权限

扩展是中间人，负责检测 AI 的指令、转发给本地执行、把结果写回网页。

### Native Host（Rust 程序）

- **能做**：执行命令、读写文件、管理后台进程
- **不能做**：读网页内容、直接和 AI 通信
- **原因**：独立进程，只能通过 HTTP 和扩展通信

Native Host 是真正执行操作的程序。

### 用户

- **能做**：发消息、点"注入提示词"按钮
- **不能做**：直接控制检测和执行流程
- **原因**：自动循环启动后，用户是等待结果的角色

## 完整工作流程

```
1. 用户打开 AI 聊网页
2. 扩展自动识别平台，加载对应适配器
3. 用户点"注入提示词"→ 系统提示词写入对话框
4. 用户发任务（如"创建 Flask 待办应用"）
5. AI 回复中输出 tool_call 代码块
6. 扩展在 DOM 中检测到这段文字
7. text-parser 解析出工具名和参数
8. Agent Loop 通过 HTTP 发给 native host
9. Native Host 执行操作
10. 结果通过 HTTP 返回
11. 扩展把结果写入对话框，点发送
12. AI 看到结果，继续生成下一步
13. 循环直到任务完成
```

## 通信协议

AI 和扩展之间通过文本格式通信：

```
tool_call
===
工具名
---
参数名1: 单行值
参数名2: <<<
多行内容
>>>
===
```

- `===` 是边界标记，分隔多个 tool_call
- `<<<`/`>>>` 包裹多行内容
- `---` 分隔参数

这个格式是通过系统提示词教给 AI 的，扩展在 DOM 中检测这个格式。

## Agent Loop 状态机

```
IDLE → DETECTING → EXECUTING → INJECTING → WAITING → IDLE
```

- **IDLE**：空闲，等待 AI 输出
- **DETECTING**：正在检测和解析 tool_call
- **EXECUTING**：正在执行 tool_call
- **INJECTING**：正在把结果注入对话框
- **WAITING**：等待 AI 开始下一轮生成

对讲机模型：一问一答，严格单线程。检测到 tool_call → 执行 → 注入结果 → 等待 AI 回复 → 再次检测。

## 平台适配器

每个 AI 平台的网页结构不同，需要单独写适配器。适配器需要实现三个核心接口：

| 接口 | 作用 |
|------|------|
| `isGenerating()` | AI 是否在生成中 |
| `getLastAIMessageElement()` | 获取最后一条 AI 消息的 DOM 元素 |
| `findSendButton()` | 找到发送按钮 |

这三个接口的返回值决定了整个链路通不通。
